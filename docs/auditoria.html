      1. Resumo executivo

      O Flix (GEFlix) é dois produtos no mesmo app Next.js. A biblioteca em / organiza YouTube pessoal (categorias, coleções, histórico). O catálogo em /catalogo é a vitrine paga: arquivo MP4/WebM/MOV no disco, player autenticado, paywall por plano. Visitante assiste o free sem conta; Premium (R$ 10/mês) e Pro (R$ 17,90/mês) desbloqueiam o resto depois que o admin confirma o PIX. Não é marketplace nem curso com módulos — é clube de um criador.

      Banco local conferido em 15 set 2026: 8 usuários (2 admin, 6 user), 21 vídeos, 3 publicados, 3 assinaturas, 3 pagamentos. A exclusão de conta já é anonimização LGPD (deleteUserAccount): preserva PlanPayment. A FK PlanPayment_userId_fkey no MySQL live é RESTRICT. Não há motivo para reescrever o produto.

      O achado que muda a prioridade: o README e o POST de criação/upload do catálogo dizem que só admin publica, mas o dono de qualquer vídeo ainda consegue publicar. PATCH e DELETE em /api/catalog/[id] usam requireUserId + dono, não requireAdmin. A UI esconde o botão “Publicar” do header para não-admin, mas mostra Publicar/Despublicar em todo card mine. No banco live o vídeo 22 (upload, publicado, plano free) pertence ao usuário 3 com role user. A vitrine deixa de ser só do criador.

      Segundo achado comprovado no information_schema: ConsentimentoLgpd está em MyISAM e não tem FK no banco live — a migration declara InnoDB+FK, o MySQL live não aplicou. RateLimitBucket e PlanPayment estão em InnoDB. Sem achado crítico (nada bloqueia nem corrompe pagamento).

      3. Funcionalidades já implementadas

      Clube do criador (o que vende)

      Upload em /admin/videos e POST admin em /api/catalog + /api/catalog/upload (MP4/WebM/MOV até 3 GB, magic-bytes). Plano mínimo por vídeo. Stream privado com Range, ETag e private, no-cache. Visitante free; assinante vê conforme o plano. Grants extras (presente / cliente). Favorito e progresso por usuário.

      Cobrança e operação

      /plano pede upgrade, mostra PIX, envia comprovante. Admin aprova em /admin/solicitacoes, registra pagamento, renova / cancela assinatura. Cron diário: vence em 7 dias, atraso, expiração e rebaixa o plano. Auditoria, CSV, health, LGPD (export JSON + anonimizar). CSRF de Origin em /api/*. Rate limit MySQL em login/cadastro/recuperação.

      Biblioteca pessoal (não é a loja)

      / é organizador de YouTube: categorias, notas, coleções com link /c/[token], histórico, estatísticas, cota 20 / 100 / ilimitado. POST /api/videos cria só source=youtube, published default false. Arquivo autoral entra pelo catálogo/admin, não por essa tela.

      4. Problemas encontrados

      Alto Dono não-admin publica e apaga no catálogo

      Onde: app/api/catalog/[id]/route.ts:20-31 (PATCH), :88-99 (DELETE); lib/video-grants.ts:99-111; app/catalogo/page.tsx:364-368; grants em app/api/catalog/[id]/grants/route.ts:18-27.

      O que é: POST create/upload exige requireAdmin (catalog/route.ts:131-132, upload/route.ts:29-30). PATCH/DELETE/grants aceitam qualquer dono. GET público lista published: true sem filtrar role do dono. Um user autenticado pode PATCH /api/catalog/{id} com { published: true } num vídeo da biblioteca (mesmo modelo Video) e aparecer na vitrine. A UI ainda mostra Publicar em card mine.

      Impacto: a loja deixa de ser só do criador; o PIX continua na chave do dono. No MySQL live o vídeo 22 (upload publicado, userId 3, role user) já está na vitrine.

      Solução: requireAdmin() em PATCH/DELETE/grants do catálogo (ou pelo menos no campo published); esconder ações de card para não-admin; decidir o que fazer com o vídeo 22. Testes em route.test.ts dessas rotas. Complexidade baixa.

      Médio ConsentimentoLgpd MyISAM sem FK no banco live

      Onde: information_schema (ENGINE=MyISAM; tabela ausente de REFERENTIAL_CONSTRAINTS). Schema Prisma declara FK Cascade (schema.prisma:266); migration 20260916090000_lgpd_soft_delete cria a FK. Única tabela MyISAM no schema atual.

      Impacto: o app anonimiza em vez de apagar o User, então hoje não explode. Hard-delete ou restore de backup pode deixar consentimento órfão. RateLimitBucket já foi corrigido pelo mesmo padrão (20260917100000_rate_limit_innodb).

      Solução: migration ALTER TABLE ConsentimentoLgpd ENGINE=InnoDB + recriar ConsentimentoLgpd_userId_fkey. Complexidade baixa. Aceite: query no information_schema.

      Baixo Miniatura publicada sem paywall

      Onde: app/api/videos/[id]/thumbnail/route.ts:26,44 — visitante vê thumb se published; cache public, max-age=86400. O stream do vídeo continua paywalled.

      Impacto: frame JPEG de aula paga vaza; não libera o arquivo. Solução: exigir o mesmo canAccessCatalogVideo do stream, ou aceitar como preview de vitrine. Complexidade baixa.

      Baixo JWT engole erro de banco

      Onde: lib/auth.ts:119-121. Se o MySQL cair no callback JWT, o token antigo (role/status) permanece. APIs com requireUserId ainda consultam currentDbUser. Impacto só se a UI confiar no JWT sem bater na API. Complexidade baixa.

      Baixo Stream por ID permanente

      Onde: /api/videos/[id]/stream — auth por sessão/plano, não URL assinada. README já documenta R2/URL assinada quando o Node saturar. Não é vazamento anônimo. Adiar até volume real.
